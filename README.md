Наш скрипт №2 не изменяет постоянные банковские таблицы, но может создавать существенную нагрузку на процессор, диски, оперативную память и `tempdb`.

Особенно на этапе `stage = 2`, где мы обращаемся к трём крупным источникам: платежам, активности приложений `ods_cli_devices` и истории закрытий вкладов `DepositContract_all`.

Для проверки собственной нагрузки необязательно иметь административные права или доступ к `master`.

## 1. Проверить, сколько места занимают наши временные таблицы

После завершения очередной порции скрипта выполни в том же окне SSMS:

```
EXEC tempdb.sys.sp_spaceused N'#rk26p_cli';

IF OBJECT_ID('tempdb..#rk26w_msg') IS NOT NULL
    EXEC tempdb.sys.sp_spaceused N'#rk26w_msg';

IF OBJECT_ID('tempdb..#rk26w_event') IS NOT NULL
    EXEC tempdb.sys.sp_spaceused N'#rk26w_event';

IF OBJECT_ID('tempdb..#rk26w_agg') IS NOT NULL
    EXEC tempdb.sys.sp_spaceused N'#rk26w_agg';
```

| Показатель   | Значение                                   |
| ------------ | ------------------------------------------ |
| `rows`       | Количество строк                           |
| `reserved`   | Всего зарезервировано места в tempdb       |
| `data`       | Размер данных                              |
| `index_size` | Размер индексов                            |
| `unused`     | Зарезервированное, но неиспользуемое место |

Для `sp_spaceused` по умолчанию достаточно прав обычного пользователя.&#x20;

## 2. Проверить нагрузку собственной сессии

Также в том же окне:

```
SELECT
    session_id,
    cpu_time / 1000.0 AS cpu_seconds,
    memory_usage * 8.0 / 1024 AS session_memory_mb,
    reads,
    writes,
    logical_reads,
    open_transaction_count
FROM sys.dm_exec_sessions
WHERE session_id = @@SPID;
```

Эти показатели преимущественно накопительные за время существования соединения. `session_memory_mb` — память сессии, а не вся память, используемая запросом.

Свою сессию можно просматривать без административных прав.&#x20;

## 3. Проверить нагрузку непосредственно при выполнении скрипта

Попробуй добавить в самое начало скрипта №2:

```
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

В конце:

```
SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;
```

Во вкладке Messages появится статистика выполнения отдельных запросов:

| Показатель              | Что показывает                          |
| ----------------------- | --------------------------------------- |
| `CPU time`              | Затраты процессорного времени           |
| `elapsed time`          | Фактическое время выполнения            |
| `logical reads`         | Количество обращений к страницам данных |
| `physical reads`        | Чтение страниц с диска                  |
| `Worktable`, `Workfile` | Обращения к внутренним рабочим объектам |

Для этого не требуется разрешение `SHOWPLAN`.&#x20;

## 5. Что рекомендую сейчас

Для начала поставь в скрипте №2:

```
DECLARE @DaysPerRun int = 1;
DECLARE @MessageDaysPerRun int = 1;
DECLARE @MaxRunSeconds int = 180;
```

У нас уже установлен `MAXDOP 1` для основных тяжёлых запросов, что ограничивает их параллелизм.

Но имей в виду:

- `MAXDOP 1` не ограничивает потребление памяти.
- `NOLOCK` не устраняет нагрузку на сервер и не исключает все блокировки.
- `@MaxRunSeconds` не прерывает уже выполняющийся запрос.
- Без серверных разрешений нельзя полноценно оценить общую загрузку сервера и свободные ресурсы tempdb.

Если текущий запрос вызывает опасения, можешь нажать Cancel, не закрывая соединение. Дождись завершения отмены. Уже обработанные даты сохранятся.

Пришли мне результаты `sp_spaceused` и статистику `IO/TIME` за один запуск. Особенно меня интересует `ods_cli_devices` — подозреваю, что именно этот источник может оказаться самым тяжёлым.
